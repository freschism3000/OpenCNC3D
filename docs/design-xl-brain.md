# The XL Brain -- design (26 Aug 2026)

Authoritative design for the Enhanced-only engine fork that takes CNC3D past the
classic brain's ceilings, per the project owner's direction: 256x256/16 players, then 512x512/32,
then 1024x1024/64 -- modern Windows and Mac only; the Classic/Win98 build keeps the
stock engine untouched (engineering notes section 1e, the two-brain law). Produced
from the big-map recon evidence; where this doc and the code disagree once phases
land, update THIS DOC in the same commit.

## Fork shape

A REAL SOURCE COPY at brain/xl/, not ifdefs. Two hard reasons. (1) The CI law: tools/check-brain-checkout.sh enforces brain/vanilla == upstream@patches/UPSTREAM.txt + vanilla-cnc3d.patch BYTE FOR BYTE on every push, so every XL ifdef would have to ride inside that patch, turning the readable record of "our additive changes to EA's engine" into a second engine hidden in a diff; one slip re-breaks CI exactly the way the drifted checkout did in August. (2) The change is not lexically containable: the defines.h type block (1660-1745), the entire function.h inline suite (740-900), coord.cpp, const.cpp AdjacentCoord/StoppingCoordAbs tables, ~164 raw packed-literal sites across 26 files (0x00800080 / 0xFF00FF00 family), deletion of CELL_COMPOSITE touching every Cell_X/Cell_Y site, EventClass bitfields, dllinterface.h struct capacities, findpath.cpp replaced wholesale, and save layouts. An XLMAPS define would dwarf MEGAMAPS by an order of magnitude inside files the classic brain must keep byte-identical. Verdict: ifdefs are not tenable; copy and log.

LAYOUT: brain/xl/{tiberiandawn/, common/, cmake/, CMakeLists.txt} copied from brain/vanilla at a recorded fork point (tag brain-xl-forkpoint, current vanilla state including MEGAMAPS + EIGHTPLAYERS); drop redalert/ and unused targets. common/ is coordinate-free (verified: zero COORDINATE/CELL hits) and a new gate asserts brain/xl/common == brain/vanilla/common byte-for-byte forever, so only tiberiandawn/ may diverge. brain/xl/DIVERGENCE.md is the divergence log, grouped by concern (types, houses, pathfinder, ABI, formats); a suite gate lists files differing from the forkpoint tag and fails when any changed file lacks an entry (same spirit as the changelog rule). Upstream re-pins port to xl by hand with a DIVERGENCE.md entry; that manual cost is the honest price of the fork. The fork is GPL like vanilla and ships in whatever source publication accompanies releases.

BUILD: CMake target TiberianDawnXL (add_library SHARED, PREFIX "", same shape as TiberianDawn at vanilla CMakeLists.txt:207-232, its own commonr build from xl's common/), defines TIBERIAN_DAWN + XLMAPS with the MEGAMAPS/EIGHTPLAYERS ifdefs collapsed to their XL values inside the fork; XLMAPS is not an option, the tree IS the fork. Output TiberianDawnXL.dylib / TiberianDawnXL.dll. tools/mac/build-brain-xl-mac.sh mirrors build-brain-mac.sh including the CMAKE_OSX_DEPLOYMENT_TARGET otool assertion. release.sh ships BOTH dylibs in Enhanced zips; the Tier 1 / Win98 zip never carries XL.

HOST SELECTION: the map INI is the authority. [Map] Width/Height > 128, or an explicit [CNC3D] Brain=XL, selects the XL brain (same pattern as edit_pack_for resolving the pack from the map's own INI). find_brain (cnc_eyes.cpp:13977) grows XL candidates: ../brain/lib/TiberianDawnXL.dylib, ../brain/xl/build-native/tiberiandawn/TiberianDawnXL.dylib, beside-binary CNC3D_BRAIN_XL_LIB; plus a --dylib-xl override. Both brains stay loaded side by side: dlsym/GetProcAddress resolve per handle and statics are per image, so the existing Brain* function-pointer set becomes struct BrainVTable with two instances and g_brain pointing at the active one. Classic boots at startup exactly as today; XL loads lazily on the first XL map. The restart-in-place shortcut in boot_brain (re-calling CNC_Start_Custom_Instance) must first check that the target map's brain equals the running one, otherwise swap g_brain and start on the other handle.

## The widened coordinate

COORDINATE: typedef uint64_t COORDINATE, X in the low u32, Y in the high u32; each axis is an ABSOLUTE LEPTON COUNT with cell = axis >> 8 and lepton-in-cell = axis & 0xFF. CELL_LEPTON_W stays 256, so every speed table, pixel ratio, and fixed-point quantum is numerically unchanged. It stays a SCALAR on purpose: !coord truth tests, == compares, union membership in EventClass, memcpy'd saves, VectorClass storage and by-value calls all survive; a struct{X,Y} would break every scalar idiom and triple the diff. COORD_COMPOSITE becomes union { COORDINATE Coord; struct { uint32_t X, Y; } Sub; } with a little-endian static_assert replacing the __BIG_ENDIAN__ arms; LEPTON becomes uint32_t (per-axis absolute) and the nested LEPTON_COMPOSITE dies; the few .Sub.X.Sub.Cell sites (Cell_Coord, Coord_Whole/Fraction/Snap, CNC3D_Print_One's lx/ly) rewrite to shifts.

THE INLINE SUITE (function.h:740-900) is the real chokepoint and regenerates once: XY_Coord(x,y) = ((u64)(u32)y << 32) | (u32)x; Coord_X = (int)(u32)coord; Coord_Y = (int)(coord >> 32); Coord_XCell = Coord_X >> 8; Coord_Add/Sub = two independent 32-bit axis adds with NO cross-axis carry (exactly vanilla's per-axis 16-bit semantics; the (int)(short) truncation casts die); Coord_Snap sets both lepton bytes to 0x80; Cell_Coord(cell) = XY_Coord((Cell_X(cell) << 8) | 0x80, (Cell_Y(cell) << 8) | 0x80); XYP_Coord / Lepton_To_Pixel / Pixel_To_Lepton unchanged in form.

BIT-IDIOM REGENERATION (the 164 sites in 26 files, mechanical): 0x00800080 cell-centre becomes constexpr COORD_CENTER = 0x0000008000000080ULL; 0xFF00FF00 keep-cell mask becomes 0xFFFFFF00FFFFFF00ULL; 0x00FF00FF fraction mask becomes 0x000000FF000000FFULL; AdjacentCoord[8] (const.cpp:176) and the StoppingCoordAbs quincunx regenerate as two's-complement per-axis deltas built by a constexpr XY_Delta(dx,dy) maker, never hand hex again. HIGH_COORD_MASK is REBORN with real slack: 0xFFF00000FFF00000ULL (bits above 2^20 leptons = 4096 cells per axis) catches both negative wrap and overrun in one AND, so Coord_Scatter/Coord_Move guards keep their exact shape; this permanently kills the recon's "256 exactly fills the type and the guard dies" trap.

CELL: typedef int32_t CELL. CELL_COMPOSITE and its zero-width sluff bitfield are DELETED (taking the big-endian trap and the exactly-full-16-bit wraparound trap with them). Cell_X(cell) = cell & (MAP_CELL_W - 1); Cell_Y = cell >> MAP_CELL_MAX_X_BITS; XY_Cell(x,y) = (y << MAP_CELL_MAX_X_BITS) | x. MAP_CELL_MAX_X/Y_BITS = 10 FROM THE FIRST XL COMMIT: one 1024-wide address space for the whole ladder, so 256, 512, 1024 are content tiers, not repeated brain re-breaks; smaller XL maps live confined in the 1024 stride exactly as 64-wide content lives in MEGAMAPS' 128 stride today (Confine_Old_Cell generalizes to (cell % 64) + (cell / 64) * MAP_CELL_W). MAP_CELL_W stays compile-time: a runtime-variable width would touch every +/-MAP_CELL_W offset table (MoveSpillage, AdjacentCell, REFRESH lists) for zero ladder benefit. MAP_CELL_TOTAL = 1,048,576; MapClass::Array is already a heap VectorClass<CellClass> (map.h:168), about 120MB at 64-bit pointers, acceptable on the modern-only target; full-MAP_CELL_TOTAL housekeeping loops get rect-trimmed in the 512 phase.

TARGET: UNCHANGED. int with 24-bit mantissa / 8-bit exponent holds cell numbers to 4096x4096 (1024x1024 is 2^20) and heap ids trivially; As_Cell/As_Target only change signature width to int32 CELL, not encoding. EventClass Target/NavCom/TarCom wire fields and TARGET save layouts stay put.

PRECISION AND FEEL: leptons stay 256 per cell, so Move_Point's CosTable/SinTable quantum, all MPH speed accumulation, and Distance_Coord's integer dragon-strike produce bit-identical per-tick motion. The audit is the (short) axis truncations: Coord_Move's short x/y locals, every (short)/(LEPTON) cast near coordinate math widens to int32 (values cap at 2^20, exact). The parity gate in the phases proves it: same mission, classic vs XL, identical dumps tick by tick. Only route CHOICE changes later, when the pathfinder swaps; per-cell movement never does. PHASE 1 FINDINGS the contract now carries (26 Aug 2026): (1) THE SCAN-WINDOW RULE -- MapClass::Logic's tiberium sweep is chunked off MAP_CELL_TOTAL and its candidate lists were sized off MAP_CELL_W, and both feed the one seeded random stream, so scan GEOMETRY follows the SCENARIO FORMAT, not the stride: classic-format scenarios sweep the classic 128-wide window at the classic cadence with the candidate lists pinned at the classic 64 capacity (TIBERIUM_LIST_MAX), XL-native scenarios sweep the full stride. Any future stride-keyed scheduler must obey the same rule or classic-content replay shears. (2) CELL == int == TARGET erases an overload distinction; retirements of CELL overloads are enumerated by a scratch build with `typedef long CELL` (every former caller turns into an ambiguity error), never by grep. (3) The [Base] INI section stores CLASSIC PACKED 32-bit coordinates as decimals; the XL reader unpacks per-axis and the writer re-packs, keeping classic INIs round-trip identical. (4) The never-placed-object sentinel 0xFFFFFFFF widens to ~0ULL (all-ones in BOTH axes).

## 64 houses

ENUM GROWTH, NOT DYNAMIC HOUSES, WITH ONE STRUCTURAL MOVE: multi-first ordering. Arithmetic forces it: 4 campaign houses + 64 multi houses = 68 indices, and every mask shifts by FULL HousesType index, so u64 overflows for the tail four. XL reorders the enum: HOUSE_MULTI1 = 0 .. HOUSE_MULTI64 = 63, then HOUSE_GOOD = 64, HOUSE_BAD, HOUSE_NEUTRAL, HOUSE_JP = 67; HOUSE_COUNT = 68 (char-based enum survives, 68 < 127). All u64 masks then cover exactly the 64 multi slots. Campaign houses carry NO mask bits; the XL brain REFUSES GAME_NORMAL scenarios at load (campaign is classic-brain territory under the two-brain law), and Is_Ally(h) for h >= 64 resolves by rule (self only; civilians stay hostile-neutral) with a debug assert. The port audit this buys: every comparison shaped like h >= HOUSE_MULTI1 or loops starting at HOUSE_GOOD gets reviewed once (grep-able, finite). Fallback if the audit finds a swamp: cap at 60 players so 4+60 fits u64 unordered; that is the project owner's call to pre-approve, and the reorder is the recommendation.

MASKS to uint64_t: CellClass::IsMappedByPlayerMask / IsVisibleByPlayerMask (cell.h:149/154), HouseClass::Allies + Get_Allies (house.h:489/743), the ObjectClass IsSelectedMask / IsDiscoveredByPlayerMask family, and Ownable (type.h u16 to u64, fixing the recon's latent truncation: TechnoClass::Get_Ownable returning unsigned char at techno.h:247/object.h:188). Mechanical law: every 1 << house becomes 1ULL << house; a grep-gate over brain/xl enforces no bare "1 <<" against a house index. Mask scans iterate ascending bit index for determinism.

EVENTCLASS: Frame:27 to 24 (12.9 days at 15Hz), ID:4 to 7 (house index to 67), IsExecuted:1; exactly 32 bits again. The MPlayerID color<<4 nybble identity dies: replaced by explicit u8 ColorSlot + u8 ActLike fields (wire grows one byte; XL replay/wire is XL-only so nothing external breaks).

CAPACITIES: MAX_PLAYERS = 64 (defines.h:2592 block); MAX_MULTI_NAMES >= 64 to satisfy the score-row static_assert (defines.h:2881). Heap caps scale for 64 armies: UNIT_MAX / INFANTRY_MAX / BUILDING_MAX 500 to 4000, AIRCRAFT_MAX 100 to 800 (EACH_* derive; TARGET's 24-bit mantissa is indifferent). hdata.cpp's 64 HouseTypeClass entries + Pointers rows generate from one X-macro table (IniName "Multi1".."Multi64"), not 64 hand-written blocks. Waypoints: XL INIs use RA-style numeric waypoints; Scen.Waypoint grows to WAYPT_COUNT = 130 with starts 0..63, WAYPT_HOME = 128, WAYPT_REINF = 129; the way[26] letter-parse cap dies in xl's INI reader. dllinterface.h: MAX_HOUSES 32 to 68; AllyFlags/SpiedPowerFlags/SpiedMoneyFlags u32 to u64; GAME_OVER_MULTIPLAYER_MAX_PLAYERS_TRACKED 8 to 64; SpiedInfo[68].

COLOR IDENTITY, THE BRAIN/HOST CONTRACT: the brain keeps its PlayerColorType palette remaps and lets them repeat past ~8; its 8-bit rendering output is unused by CNC3D anyway. What the HOST needs is stable identity, and the dump provides it: the HOUSE| line (dllinterface.cpp:8401) grows |slot=%d|color=%d|side=%s where slot is the multi index 0..63 (stable all session), color is the brain's ColorIndex, side is ActLike GDI or NOD. OBJ| already names the owner house (IniName) which resolves to that HOUSE| row. The host picks the pack's livery by side (the existing two-livery gdi_data scheme survives untouched) and applies a per-slot tint from a host-side 64-entry palette data file (the project owner-tunable, cnc3d-fx.cfg style); obj_is_gdi (cnc_eyes.cpp:2071) becomes a slot+side lookup and house_colour (cnc_eyes.cpp:4094) reads the palette, which automatically fixes radar dots, health bars and selection since all route through house_colour already.

SIDEBAR/SCORE/RADAR: sidebar is per-local-player through the GlyphX path and is house-count-agnostic; score screen re-dimensions MultiPlayerPlayersData to 64 rows (host draws it, so layout work is host-side); the brain's own radar class stays vestigial, the host radar handles 64 colors via the palette. PER-SESSION vs ENGINE: MAX_PLAYERS 64 is the engine ceiling; how many the lobby offers (SK_AI_MAX, roster rows) stays a host/session decision lifted in the host phases.

## Pathfinder

REPLACEMENT: plain A* with a binary heap over the cell grid, integer-only, plugged in at the EXISTING SEAM: FootClass::Find_Path(dest, final_moves, maxlen, threshhold) keeps its signature and still returns PathType* (defines.h:2565-2575), so FootClass::Basic_Path (foot.cpp), the Path[CONQUER_PATH_MAX=9] consumption, Optimize_Moves smoothing and the threat retry ladder are all untouched. The edge-follower internals (Follow_Edge, Register_Cell, Unravel_Loop, MAX_MLIST_SIZE 400 in findpath.cpp:84) are deleted in brain/xl/tiberiandawn/findpath_xl.cpp; RA shipped 128 maps on only 300 list entries, and at 256+ the 400-entry bound means corner-to-corner treks fail outright, which is the justification artifact.

WHY NOT JPS OR HIERARCHICAL: JPS assumes uniform edge costs and TD's GroundType::Cost[SPEED] varies per cell (tiberium, rough), so JPS is invalid without cost extensions; HPA* adds cluster maintenance and a second determinism surface with no demonstrated need. A PathEngine seam is left in findpath_xl.cpp; hierarchy is built only if the 512 perf gate fails.

MECHANICS: neighbors are the 8 facings expanded in FIXED FacingType order (N..NW); passability and cost through Can_Enter_Cell(cell, facing) with the caller's MoveType threshold, the same world model the edge-follower consulted; g-cost is int32 in scaled units (straight 100, diagonal 141, terrain cost multiplied in from GroundType); h is integer octile, 100*max(dx,dy) + 41*min(dx,dy), admissible; threat cells add a flat integer penalty tier reproducing the threat_stage escalation semantics.

MEMORY AT 1M CELLS, allocated once per brain instance and reused: g int32[1M] = 4MB, parent-direction u8[1M] = 1MB, visited stamps u16[1M] = 2MB using a generation counter so there is no per-search memset (exact-compare stamps are deterministic), heap array worst-case 4MB; about 11MB steady, recorded in DIVERGENCE.md.

BOUNDS AND OUTPUT: node-expansion cap (initially 65,536); on cap or unreachable, return the path to the touched node nearest the destination, matching the partial-path behavior Basic_Path already tolerates. PathType::Command comes from a heap buffer sized to the real path (the stack FacingType[402] pair dies), reconstructed by walking parent directions backward then reversed, then Optimize_Moves runs as before.

DETERMINISM: the heap orders by (f, g, cell number, insertion serial), a total order with no floats anywhere in the file (grep-gated), so expansion order is machine-independent; repath scheduling stays event-driven as vanilla, and if the 64-player storm profile shows tick spikes, a deterministic FIFO repath budget queue ordered by heap id is the designed relief valve, built only when the perf gate demands it.

INTERIM: the 256 bring-up phase may run the old edge-follower (it compiles fine over int32 CELL) with MAX_MLIST_SIZE / MAX_PATH_EDGE_FOLLOW bumped 400 to 1200 as scaffolding, but the 256/16 tier does NOT ship on it; long-trek stalls read as bugs.

## ABI and host

ABI (brain/xl/tiberiandawn/dllinterface.h): MAX_EXPORT_CELLS 128*128 to 1024*1024. CNCMapDataStruct's embedded StaticCells[MAX_EXPORT_CELLS] becomes ~36MB (36B * 1M), and CNCPlayerInfoStruct::ActionWithSelected[MAX_EXPORT_CELLS] ~4MB, so ALL host fetch buffers for these go heap (the current global/stack pattern dies); keep the struct SHAPES first, and only convert STATIC_MAP to a count-prefixed rect fetch later if profiling objects. The Count-prefixed variable exports (shroud, dynamic map, layers) scale untouched; the stride-sensitive u8 cell fields widen: CNCPlayerInfoStruct::HomeCellX/Y and CNCDynamicMapEntryStruct::CellX/Y to u16. House fields per houseDesign (MAX_HOUSES 68, u64 flags, 64 tracked players). NEW, cheap in the fork: export CNC3D_ABI_Facts(struct CNC3DAbiFactsStruct*) carrying {abi_version, map_stride=1024, max_export_cells, max_houses, max_players, sizeof(CNCMapDataStruct), sizeof(CNCPlayerInfoStruct), sizeof(CNCShroudEntryStruct)}; the host asserts at dlopen and refuses a mismatched dylib loudly, closing the recon's "structs only match because both sides define the same macros, no negotiation" hazard on the forkable side.

HOST, ONE PROCESS TWO ABIS: game/brain_vtable.h defines struct BrainVTable (every existing Brain* pointer plus stride and limits); two adapter TUs, game/brain_classic.cpp (includes vanilla dllinterface.h with TIBERIAN_DAWN+MEGAMAPS exactly as cnc_eyes.cpp:170-181 does today) and game/brain_xl.cpp (includes the xl header), each normalizing map dims, static cells, shroud entries and player rows into host-neutral structs. This is the one real host refactor and it permanently kills the silent-struct-mismatch bug class.

DUMP PROTOCOL: nearly free, by design of the honest fields. The host OBJ| parser (cnc_eyes.cpp:3100-3165) already reads per-axis x=, y=, lx=, ly=, clx=, cly=, tcx=, tcy= and IGNORES newcell/inicell/centercell, so object placement survives XL untouched. Three additions: OBJDUMP-BEGIN gains a MAPMETA|stride=%d|w=%d|h=%d|players=%d line so gates and tools never infer stride; inicell= emits -1 for XL-native scenarios (it is the y*64+x legacy convention, meaningless past 64-wide content); HOUSE| gains slot/color/side. Dump volume at 4000-unit heaps is ~1-2MB/tick through capture_brain_call's temp file; measure in the 1024 phase and add a dirty-only mode only if the profiler demands.

C3D_MAP_MAX SEAM: cnc_eyes.cpp:904's #define and the static_assert at :909 tying it to the brain's MEGAMAPS width become runtime dims off the pack header and CNC3D_ABI_Facts. The static C3D_MAP_MAX^2 arrays go heap at pack load: g_cellHoles (:1229), the g_bldCellNow/Prev/DeadKey/HouseNow/DeadHouse/DeadTtl family (:2728-2793), the (C3D_MAP_MAX+1)^2 corner grids, screen_to_cell and camera GRID bounds, the shroud 65-corner coverage array (the shroud CELL layer is already dynamic). Memory at 1024: ~25MB cell list + ~3MB corners + ~9MB working grids; fine on modern hosts.

PACK FORMAT v2: the CNC3DPKE header gains width/height, and the PK9 (65x65 corner heights), PKC (65x65 tint) and PKD tails become length-prefixed instead of EOF-relative with 4225/8450 baked in; both writers change (game/bake5.py AND tools/bakery/bake5.py, whose :2561 exact-offset asserts die) plus the one reader (load_pack in cnc_eyes.cpp); v1 packs stay loadable (no prefix implies 65x65). BAKERY QUADRATICS: n64_terrain.py (tools/bakery/sharecopy/assets/terrain/) must SKIP or TILE its whole-map composite PNG above 256 (about 1.8GB at 1024); .BIN/.MAP grow to W*H*2, .HGT to (W+1)^2, the corner grid to (W+1)^2.

RADAR AT 1024: hud640.c's 120px surface means 8.5 cells per pixel; replace the integer zoom floor (hud640.c:256) with a host-maintained downsampled occupancy grid (max-pool 8x8, updated incrementally from the dump diff) plus a view rectangle overlay. EDITOR: heap-sized grids, minimap resample, playtest confinement unchanged; the 8192-byte BIN reader/writer in edit_mod.h and its 64-stride tables die in the classic size-agnostic rung already underway; XL maps author as INI [Map] Version=1 with numeric waypoints.

## Determinism strategy

The XL brain inherits vanilla's frame (one seeded RNG, tick-locked logic); the fork adds exactly three risks: widened arithmetic changing values, the new pathfinder's iteration order, and UB uncovered by new value ranges. Strategy, in the order it catches things:

(a) THE PARITY ORACLE (phases 1-3): classic-vs-XL per-tick dump equality on the same classic content. Any widening slip (a surviving (short) cast, a 1<< that needed 1ULL<<, a truncated axis, a wrong regenerated literal) surfaces as a first-divergent-tick with a field-level diff. The comparator lives in tools/xl-parity/ and normalizes only stride-derived fields (newcell/centercell/inicell, MAPMETA). It is retired when the pathfinder lands (route choice legitimately diverges) and archived, not deleted.

(b) TWO-RUN DUMP-HASH GATE, permanent, modeled on G36c (N runs, one distinct digest): a scripted session hashes the concatenation of OBJ dumps every 15 ticks plus shroud digests and HOUSE lines. NEVER hash save files; missing.md:1614 is law (raw vptrs under ASLR make save bytes irreproducible); saves are gated G54-style instead: save at frame N, advance, load, and the OBJECT DUMP must return byte-identical.

(c) INTEGER LAW: no float/double token in any sim-path file under brain/xl/tiberiandawn (grep-gate, with the dead display/audio files excluded by list); all pathfinder math int32/int64; negative division/modulo relies on C++11 defined truncation, noted in DIVERGENCE.md.

(d) ITERATION ORDER: the A* heap's total order (f, g, cell number, insertion serial); u64 mask scans ascend bit index; house loops ascend HousesType; heap-index iteration everywhere as vanilla does it; no pointer-keyed containers in any new code (addresses are ASLR'd).

(e) CROSS-ARCH AND LAYOUT: once per phase, the dump-hash gate runs on arm64 and x86_64 and the digests are compared, catching UB that same-machine runs hide; ABI and SAVED struct layouts are pinned by a static_assert translation unit (sizeof and offsetof of every dllinterface struct and every file.Write'd class), so struct packing drift becomes a compile error, not a desync.

(f) THE NET: all XL gates join the one suite; tools/release.sh already refuses on any red gate and on a missing changelog entry, and the DIVERGENCE.md-entry-per-changed-file gate keeps fork review honest. Determinism regressions therefore cannot ship; at worst they cost a suite run, which is the system working.

## the project owner's decisions (26 Aug 2026)

## Open questions for the project owner

1. NETWORKING SCOPE: is XL 64-player AI-skirmish only, or is human multiplayer on XL ever in scope? The legacy peer wire (546-byte IPX mesh, CONNECT_MAX, MAX_EVENTS 256/frame) is unusable past ~16 and human MP means a client-server layer, effectively a separate project. The design assumes AI-skirmish only; the event wire is still widened for replay integrity.

2. SAVE COMPATIBILITY: recommendation is XL saves load only in XL and classic saves only in classic, no cross-loading (a translator is real work with no player story). Confirm, so the slot records can carry a brain tag and refuse politely.

3. CAMPAIGN ON XL: the multi-first house reorder leans on "the XL brain refuses GAME_NORMAL", which keeps campaign houses maskless. If campaign-on-XL is ever wanted, the alternative is a 60-player cap (4+60 fits u64 without the reorder). Cheap to choose now, expensive later. Which is it?

4. DOES 256/16 SHIP BEFORE THE NEW PATHFINDER? The design treats Phase 4 as a ship-blocker for the tier because edge-follower stalls on long treks read as bugs. the project owner can overrule and ship the tier early with the bumped 1200-entry scaffolding, accepting visible stalls.

5. HUD AT XL SIZES: does Enhanced keep the DOS sidebar and radar (radar becomes an 8.5-cells-per-pixel windowed view at 1024) or get an Enhanced HUD variant? Decides real scope in phases 5-6.

6. THE 64-TINT PALETTE: who authors it (a the project owner-tunable data file in the cnc3d-fx.cfg pattern is the design), and is two players sharing a livery (same side art, different tint) acceptable presentation, or do liveries need to multiply?

7. MAP AUTHORSHIP AT 512/1024: editor-first (pulls editor XL work earlier in the ladder) or a couple of hand-built flagship maps first? Changes the order inside phases 5-6.

8. PACKAGING: Enhanced zips always carry both dylibs (about 2MB extra, one artifact, no version skew; the recommendation) or XL as a separate launcher asset?

9. HEAP CAPS ARE GAMEPLAY: 4000 units / 4000 infantry / 4000 buildings / 800 aircraft at 64 players (EACH_* per-player derivations follow). These are tuning numbers the project owner may want different, and they gate perf budgets.

10. WAYPOINT AUTHORING: confirm XL maps may use RA-style numeric [Waypoints] (0..129) while classic maps keep the letter namespace, so the editor writes per-format.
